# martom-ai

**martom-ai** is an agentic RAG advisor for Željezarija Martom, a hardware store in Čitluk (BiH). It is fence-first (guided advice and a materials list), and it also searches the whole store catalogue (~2,600 OLX listings).

- Source of truth: `docs/PLAN.md`. Screens: `docs/mockups/`, synced from the design canvas, which is the source of truth for design (change the canvas first; see `docs/mockups/README.md`). Read both before your first task. Fence business rules (posts, clips, corners, gates, "po narudžbi" items): `docs/domain/fence-rules.md`, confirmed by Toni; read it before any BOM, clarify, cart, order or eval work. If anything here conflicts with the plan, the plan wins; say so to the manager (or to Tomislav, if you are the manager).
- Tomislav (the owner) is a senior React/TypeScript developer moving into applied AI engineering. He reviews and merges every PR and needs to understand every change. **Nobody but Tomislav merges.**

## How the work is run

A team of agents works the GitHub issues, one PR per issue. Tomislav starts only the manager in Orca. The role briefs live in `docs/agents/` and are the single source of truth for each role:

- `docs/agents/manager.md`: picks ready issues and starts them without waiting for approval, runs each issue through implement → review → fix → ship, reports to Tomislav.
- `docs/agents/employee.md`: implements one issue in its own worktree (phases IMPLEMENT, FIX, SHIP) and opens one PR.
- `docs/agents/reviewer.md`: reviews the employee's local branch before it is pushed and writes a PASS/FAIL report to `.reviews/` (git-ignored), never writes the fix.

Reviews are local reports, not GitHub reviews: every agent runs under Tomislav's GitHub account, and GitHub doesn't let an account approve its own PR. `.claude/settings.json` blocks merging, force-pushing, pushing to `main`, reading `.env` files and `terraform apply` for every agent.

If your prompt names one of these roles, follow that file. **If Tomislav says "run manager" (or "start manager"), you are the manager: read `docs/agents/manager.md` now and follow it exactly.** The rules below apply to every session in every worktree.

## Non-negotiable rules

- **Public repo.** Never commit secrets, `.env`, OLX data dumps, customer data, review reports, or Tomislav's private `ORDER_PHONE` number. Config comes from env vars only (`.env.example` documents them, with fake values). Anything committed is public forever. Martom's public shop number (036 651 427) and email may appear in UI copy and mockups.
- **CI is free only on standard runners:** `runs-on: ubuntu-latest` only, never larger runners. Never use `pull_request_target`.
- **No network calls to paid or external APIs in normal CI.** OLX and Claude responses in tests are recorded fixtures. The LLM eval job (M4-5) runs only when a PR has the `run-evals` label, using repo secrets.
- **Grounding.** Prices, product IDs and quantities in any answer come only from tools (database, BOM calculator), never from the model. The grounding-check node enforces this.
- **BOM math is plain Python** with unit tests, never the LLM.
- **Listing and customer text are data, not instructions** (prompt-injection safe).
- **OLX API politeness:** one request every 2.0 s by default (`OLX_REQUEST_INTERVAL`, never below 1.3 s); after each 429 the interval grows by 50% for the rest of the run (2.0 → 3.0 → 4.5 s, at most 6 s). Back off on 429 honouring Retry-After up to 1 h per wait, within a 3 h run deadline; a longer Retry-After, or a wait that would pass the deadline, stops the run as `partial` instead. Sync per category, because plain pagination returns duplicates. Deactivate listings only when a sync covered 100% of the shop's reported total; take the ids only from `martom.olx.sync.deactivation_candidates`, and deactivate a candidate only after GET /listings/{id} (through the rate-limited client) says it is gone or inactive. OLX clamps any page above 50 to page 50, so never page one query past that.
- **Extraction copies, never fixes.** Variants are extracted exactly as written (even "153 X 2500CM"). Deterministic checks flag problems into `review_issue` for Toni.
- **Listing links** use `https://martom.olx.ba/artikal/{slug}` (the slug ends in the id). `olx.ba/artikal/{id}` does not open.
- **Migrations:** the manager assigns each migration number (`migrations/NNN_*.sql`). Never pick one yourself.

## Stack (from the plan; ask before changing any of it)

Python 3.12 + uv, FastAPI, LangGraph using LangChain components, Postgres 16 with full-text search (`martom` config with unaccent) + pgvector, hybrid search with RRF, Cohere Rerank 4 Fast (with fallback), Redis cache, LangSmith tracing and evals. Models: `claude-sonnet-5-5` for the agent, `claude-haiku-5-5` for extraction, query parsing and grading.

React + TypeScript (Vite) frontend on Cloudflare Pages at the free `martom-savjetnik.pages.dev` address. The API is reached through a CloudFront distribution in front of the ALB, at its free HTTPS `*.cloudfront.net` address (no custom domain for now; CORS allows only the pages.dev origin and localhost).

Orders: our own cart (korpa, kept in the browser, same workflow as martomshop.ba), then ONE "Pošalji narudžbu" button opens WhatsApp via a click-to-chat link (`https://wa.me/<number>?text=<encoded order>`) to the owner's number from the `ORDER_PHONE` env var (E.164 format, e.g. `+385…`; Tomislav's number while testing, set as a GitHub/AWS secret; use a fake number in tests and `.env.example`). No Viber, no WhatsApp Business API. Keep the message within a length WhatsApp accepts, and save the order in `order_request` before the link opens.

AWS: ECS Fargate behind a load balancer (Redis runs as a sidecar container in the task, no ElastiCache), RDS Postgres, EventBridge Scheduler, Secrets Manager, Terraform, GitHub OIDC.

## Commands

Python 3.12 is pinned in `.python-version`; uv installs it. Code lives in `src/martom/` (src layout, package `martom`), tests in `tests/`. Ruff and pytest settings are in `pyproject.toml`.

```sh
uv sync                     # install / update dependencies into .venv
uv run pytest               # tests
uv run ruff check           # lint (add --fix to auto-fix)
uv run ruff format          # format (CI uses --check)
uv add <pkg>                # runtime dependency; `uv add --dev <pkg>` for dev-only
docker compose up -d --wait # Postgres 16 + pgvector and Redis, waits until both are healthy
uv run martom migrate       # run from the repo root
uv run martom api           # FastAPI on http://127.0.0.1:8000, JSON logs (--reload, --host, --port)
uv run martom sync          # OLX -> olx_listing, one sync_run row; --full (weekly), --apply-skipped RUN_ID, --scheduled (scheduler only)
uv run martom extract       # Haiku: active listings whose detail_hash changed -> product + product_variant; --all, --limit N
uv run martom load-knowledge # knowledge/*.md -> knowledge_chunk (run from the repo root; --dir to change)
uv run martom embed         # embed active products + knowledge chunks whose text changed (EMBEDDING_PROVIDER)
uv run martom report        # Toni's open review issues in Bosnian, by priority, with OLX links (stdout only)
```

Every worktree shares one compose stack (fixed project name `martom`); tests create and drop their own throwaway databases on it. Redis tests use `TEST_REDIS_URL` or the compose Redis on port 6379 the same way. If Postgres or Redis can't be reached, those tests are **skipped** locally (and fail in CI, where `CI` is set).

**Never source, read or print `.env`** (no `. ./.env`, `source .env`, `set -a`, `--env-file .env`): it will hold real API keys and the private `ORDER_PHONE`. Compose reads `.env` by itself for variable substitution, so **never run `docker compose config`** (it prints the resolved values). App config is the `Settings` class in `src/martom/settings.py` (pydantic-settings, env vars only, never a `.env` file); add new config there as a typed field with a safe local default. `hide_input_in_errors=True` keeps values out of validation errors; a custom validator's message must never include the value either. The API is built by `create_app()` in `src/martom/api/app.py`; log with `logging.getLogger(__name__)` and pass fields with `extra={...}`, never `print`.

Before every push: `uv run ruff check`, `uv run ruff format --check`, and `uv run pytest` with the database up. Check that the summary shows no skipped database tests before you claim they pass. CI (`.github/workflows/ci.yml`) runs the same checks, plus `martom migrate` twice against a fresh Postgres service, and the frontend checks when `web/` changed.

Migrations are plain SQL in `migrations/NNN_name.sql`, applied in number order by `martom migrate`, which records each file and its checksum in `schema_migrations` and skips files already applied. Each file runs in one transaction, so it must not contain its own `BEGIN`/`COMMIT` or `CREATE INDEX CONCURRENTLY`. Never edit a migration that has been merged; add a new one. Write every statement so it re-runs safely (`IF NOT EXISTS`, existence checks). Each table arrives in the issue that first needs it, and the manager assigns the migration number. The `martom` text search config (migration 001) is unaccent followed by the Serbian Snowball stemmer; the reasons are in that file.

`martom sync` (in `src/martom/olx/job.py`, SQL in `olx/store.py`) keeps `olx_listing` in step with OLX and writes one `sync_run` row per run. `sync_run.status` carries the outcome: `succeeded` (clean), `partial` (coverage < 100%, any detail fetch or GET re-check that still failed after its retries, or OLX stopped the run early: a Retry-After over 1 h or the 3 h deadline), `skipped_guard` (a guard skipped deactivation) or `failed`; anything but `succeeded` is alert-worthy. Ids that still failed, and the ids a run that stopped early (partial or failed) didn't get to, go in `sync_run.failed_listing_ids`, and the next nightly/full run fetches and re-checks them first. `sync_run.final_request_interval` records the interval the run ended with. A GET that succeeded on a retry doesn't change the status; it only adds to `sync_run.retried_count`, which shows trends. The CLI exits 0 / 2 (partial or skipped_guard) / 1 (failed). Inactive listings are never deleted: **search, the BOM and anything a customer sees read the `active_olx_listing` view, never `olx_listing` directly.** The view is `SELECT *`, which Postgres expands once: a migration that adds columns to `olx_listing` must re-create the view. Deactivation needs 100% coverage, a GET /listings/{id} that says 404, not "active" or another owner, and at most 10% of the active listings per run (above that it deactivates none and sets `sync_run.deactivation_skipped`, with the ids in `skipped_listing_ids`). A real large removal gets past the guard with `martom sync --apply-skipped <run id>`, or by itself when a second consecutive scheduled run trips the guard (that run deactivates only the ids flagged in both). Only scheduled nightly/full runs (`--scheduled`, set by the scheduler) count toward that streak, and the previous trip must have started at least 12 h earlier; runs started by hand never auto-apply (use `--apply-skipped`) and don't break the streak. Both re-check every id first and apply nothing when over 20% of the re-checks fail (`recheck_skipped`). A re-check error (network, timeout, 429, 5xx) never counts as removed. Fence listings outside "Ograde" are guarded, not fetched separately: `src/martom/olx/allowlist.toml` lists each id with the category it was allowlisted in (plus the fence categories, `881 = "Ograde"`), and after each nightly/full sync `guard_allowlist` (`olx/job.py`) checks that the category sync returned each one. "Synced" means returned by the category sync this run, in any category (it pages every shop category plus a whole-shop sweep): a listing returned in another category is only an INFO line ("allowlist entry redundant" in a fence category). A listing not returned gets one GET: 404, inactive, not Martom's, or still active (`not_seen`: it left every synced category) is a WARNING recorded in `sync_run.allowlist_warnings` (NULL = not checked, `[]` = fine), as is `recheck_failed` (failed GET, or a row with no category_id). A warning never changes the status or deactivates anything; the next review run raises `allowlist_listing_gone` (high, from the latest non-NULL run) or `allowlist_listing_not_synced` (medium, only from the latest non-NULL run with 100% coverage, the deactivation rule, so a partial run neither raises nor resolves it; `review/store.py` `load_allowlist_warnings`) for Toni, both without a listing_id; `recheck_failed` never reaches Toni.

`martom extract` (in `src/martom/extract/`) reads `active_olx_listing` and asks `claude-haiku-5-5` (LangChain `ChatAnthropic.with_structured_output(..., method="json_schema")`; no `temperature`, Haiku 5.5 rejects it) for an `ExtractedProduct` per listing, 4 at a time, then saves `product` + `product_variant` rows and one `sync_run` row (kind `extraction`; exit 0 / 2 partial / 1 failed). It re-extracts a listing only when `olx_listing.detail_hash` differs from `product.detail_hash`; `--all` after a prompt change. The model copies values as written (strings, never numbers); prices are parsed in Python (`extract/prices.py`) and `search_text` is built in Python (`extract/search_text.py`). Bump `PROMPT_VERSION` in `extract/prompt.py` when the prompt or schema changes, then re-record the golden fixtures with `uv run python scripts/record_extraction_fixtures.py --record` (needs `ANTHROPIC_API_KEY`; never in CI) and review the diff of `tests/fixtures/extraction/`. LangSmith traces come from `LANGSMITH_TRACING=true` + `LANGSMITH_API_KEY` in the environment; each call carries the listing id as metadata.

Toni's fence know-how lives in `knowledge/` as one Markdown file per chunk, with YAML front matter (`id`, `title`, `topic`, `sources`, `status: draft|approved`; see `knowledge/README.md`). `martom load-knowledge` (`src/martom/knowledge.py`) validates every file first and loads nothing if one is invalid, then upserts by `id` in one transaction, skips unchanged files (content hash) and deletes rows whose file is gone, so `knowledge_chunk` mirrors the folder. Only Toni's approval changes `status` to `approved`; the loader stores what the file says.

At the end of every `martom extract` run, the review checks (`src/martom/review/`) check every active listing plus `manual_products.toml` and upsert Toni's `review_issue` rows by fingerprint (sha256 of kind, listing id and a per-kind key built from values the listing wrote, such as the variant's size, colour and unit fields or the duplicates' shared title, never the message, so a reworded message or a re-extraction keeps the same row and Toni's `ignored`; only a variant with no size, colour or unit, or two variants that share them, fall back to the price and then the model-written label, see `_variant_keys`; `save_issues` never drops an issue whose fingerprint collides). One plain function per problem type in `review/checks.py`, Bosnian message, priority high/medium/low; checks only report, never change extracted data. Open issues a run no longer finds become `resolved`, with `details.resolved_because` = `not_found` or `listing_inactive` (and reopen if they come back); `ignored` stays ignored. A check that breaks makes the extraction run `partial`. A new check goes into `LISTING_CHECKS` (or `run_all_checks` for catalogue-wide ones) with unit tests, and `tests/test_review_fixtures.py` pins what the checks find on the 10 real fixture listings.

Toni's report (`src/martom/review/report.py`) is derived data: `martom report` prints it and `GET /admin/review-issues` returns it as JSON, never write it into the repo. Both read `load_open_issues`: only `open` issues, whose listing (or, for a duplicate, at least one of `details.listing_ids`) is in `active_olx_listing`, plus issues with no listing (stale manual prices), high → medium → low. Links come only from `listing_url(slug)` (`https://martom.olx.ba/artikal/{slug}`, percent-encoded; no slug = no link, never `olx.ba/artikal/{id}`). The text report strips control characters from messages and titles, since they quote listing text. Every `/admin` endpoint needs `Authorization: Bearer $ADMIN_TOKEN` (`Settings.admin_token`, at least 32 characters, compared with `secrets.compare_digest`; a shorter one stops only the API at startup, in every `APP_ENV`, via `check_admin_token`, never `Settings`, and the error never shows the value); with `ADMIN_TOKEN` unset, the API refuses to start when `APP_ENV=production` (`check_admin_token` in `create_app` and `martom api`; only the API, so a missing token never stops `martom sync` or `martom extract`), and in `local`/`test` it logs one warning and the endpoints answer 404, never open. A missing or wrong token in a request answers 401. Responses carry `Cache-Control: no-store`.

Keyword search is `search_keyword(conn, query, filters)` in `src/martom/search/keyword.py`: full-text (OR-ed words, filler words dropped in Python) plus pg_trgm word similarity over `product.search_text`, joined to `active_olx_listing`, with filters for type, height (`martom_height_cm`, ±5 cm; in "A x B" the first number is the height), colour and price (height and price must hold for the same variant; a variant priced over 0 KM is filtered on that price even on a "Na upit" listing; a listing without variants is checked against its listing price, where 0 KM or `price_by_agreement` never matches, and a 0 KM variant never matches either). It returns ids, titles and links, never prices. Both documents and queries go through the SQL function `martom_search_normalize` (migration 006: unaccent, `/` → space, "H-100" → "h 100", "153CM" → "153 cm") before the `martom` config; use it on both sides of any new full-text or trigram query. `product.search_norm` stores the normalised `search_text` (trigram GIN index); typo matches need a query word with a letter, 4+ characters and word similarity ≥ 0.55. The retrieval eval set is `evals/retrieval.jsonl` (`source: seed` until Toni's questions from #13 arrive); `martom.evals.retrieval` scores recall@5, recall@10 and MRR, plus the forbidden hit rate for cases with the optional `must_not_include_listing_ids` (ids that must not be in the top 10, e.g. the grinder for "kolica"), and `uv run python scripts/eval_retrieval.py` runs the set against the database in `DATABASE_URL`. Each search change that moves the numbers adds a row to `evals/baselines.md` (date, commit, catalogue, mode, metrics, weak cases).

Hybrid search (M3-3) is `search_hybrid(conn, query, filters, embedder=...)` in `src/martom/search/hybrid.py`: `search_keyword` and `search_vector` (`search/vector.py`, pgvector cosine distance over `product.embedding`) each return their top 30 with the same filters (`FILTERS_SQL` and `filter_params` in `keyword.py` are shared; change filters there, once), then reciprocal rank fusion (k = 60) merges them. A keyword hit found by trigram alone (`KeywordHit.text_match` False) is dropped when the listing has a vector for this model and vector search didn't return it: that drops the 'kolica' → grinder false positive (#102) without touching `MIN_TRIGRAM_SIMILARITY`, while a listing without a vector yet keeps its typo match. If the query can't be embedded within `QUERY_EMBED_TIMEOUT_SECONDS` (5 s) or the provider errors, `search_hybrid` returns keyword results alone and logs a warning; live search (API, agent) builds its embedder with `make_embedder(settings, for_queries=True)` (Cohere: one attempt, 3 s), batch runs with the default (6 attempts, 60 s per request). Evals and `compare_embeddings.py` call `search_hybrid(..., fallback=False)`: no time limit, and an embedding error is raised, so a keyword-only answer is never scored as hybrid. Needs pgvector ≥ 0.8 (`hnsw.iterative_scan`; migration 007 checks it), which the RDS engine version must provide. Embeddings go through `Embedder` (`src/martom/embeddings.py`: a LangChain `Embeddings` plus the model name stored in `embedding_model`); every vector has 1024 numbers (migration 007's `vector(1024)` on `product` and `knowledge_chunk`), search compares only vectors of the configured model, and `martom embed` (`embed_job.py`) re-embeds a row only when `text_hash(model, text)` differs from its `embedding_hash` (a product's `search_text`, a chunk's title + body; active listings only). Run it after `martom extract` and `martom load-knowledge`. `EMBEDDING_PROVIDER` is `cohere` (the default; `COHERE_API_KEY`; only models in `COHERE_MODELS`, which return 1024 numbers), `local` (open sentence-transformers models, `uv sync --group local-embeddings`; PyTorch, so kept out of the default install and the image unless a local model is chosen) or `fake` (meaningless vectors, for trying commands). Tests use fake `Embeddings` classes, never a network model. `uv run python scripts/eval_retrieval.py --search keyword|vector|hybrid` scores one search; `scripts/compare_embeddings.py` compares models (vectors cached in `data/embedding-cache/`). **Model choice (provisional):** Cohere `embed-multilingual-v3.0`, the default. On the 10 seed questions it tied e5-large and bge-m3 on recall@10 (0.95) with the best vector MRR, passed both #102 checks, needs no PyTorch in the image, and is the same vendor as the #16 rerank. With n = 10 each difference is one question, so re-run `compare_embeddings.py` when Toni's questions from #13 land. Hybrid is kept over vector alone for exact codes and SKUs (e.g. M8×80). Vector search has no relevance cutoff, so an off-topic question still gets products whenever any product passes the filters. `search_hybrid` returns `[]` only for a query of filler words alone, when the filters match no product, or when the embedding fell back to keyword and keyword found nothing. Deciding 'no results' belongs to the rerank/grading step (#16), which must handle both a full list of irrelevant products and an empty one.

BOM calculators live in `src/martom/bom/` (one module per fence system, shared types in `common.py`). Products Toni sells without an OLX listing go in the reviewed `src/martom/bom/manual_products.toml` (table name = BOM item key; name, price as a string, source, `last_confirmed`). Their prices never live in code as constants; a BOM line's `name` may repeat the product name, and a test keeps the two equal.

Every new env var goes into `.env.example` with a fake value and the milestone that first reads it. `.gitignore` drops `*.csv` and `*.jsonl` everywhere except CSV/JSONL under `tests/fixtures/` and JSONL under `evals/` (so data dumps can't slip in); put committed fixtures and eval sets there. `tests/test_fixture_privacy.py` scans every file under `tests/fixtures/` and `evals/` and fails on phone numbers, emails and seller/user fields (only 036 651 427, the martom-bekaert.com addresses, the fake 060 000 000 and Martom's own OLX shop identity pass), files over 100 KB and files with more than 20 listings; replace private numbers with 060 000 000 when you record a fixture, never widen the allowlist to make it pass. Raw OLX or database dumps go only in `/data/` (ignored); never write them elsewhere in the tree.
